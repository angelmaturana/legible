# Changelog

All notable changes to `legible` are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/): a change that makes a site which used to build stop building is a MAJOR change and is marked **Breaking**.

## [Unreleased]

### Added

- `generated_content.locale_overrides` in `src/data/site.json`: an object `{locale key: text}` that replaces any text the engine generates (home resources section, guides and blog indexes, closing strip, breadcrumb and menu labels, date format, `llms.txt` labels). Until now those texts said "your business" and could only be changed by editing `legible/locales/`, which a site must not do. The overrides are validated by the new `apply_locale_overrides()` in `legible/build.py` and every problem is reported at once, naming the key: an unknown key (with a "did you mean" suggestion), an empty or blank text, a text of the wrong kind (`months` must be a list of 12 texts), and a `{placeholder}` the default text does not receive (a placeholder may be left out, never invented; a `long_date` that `format()` cannot use is rejected). `{{markers}}` work in every override. A per-section value (`guides_index.heading`, `lead_strip.headline`…) still wins over an override. Without `locale_overrides` the output is identical byte for byte, minified and unminified, with and without guides and blog. `DOCUMENTATION.md` sections 2.1 (with a table of keys, format and placeholders), 2.4, 3.1 and 4.2 and `AGENTS.md` section 10 describe it. 17 new regression tests (`TestLocaleOverrides`, 161 → 178).
- Fast start: `legible start` followed by inputs (a style URL, fields in one line such as `name: …; activity: …`, or attached images, with `style:` and `data:` to say which image is which) skips the twelve-question interview. The AI asks only for the business name and the theme when they are missing (with only a style source, it asks the name and whether to keep the same theme), derives or leaves as `[CONFIRM …]` everything else and writes the plan with no confirmation round. Facts are never invented; descriptive example text is allowed, marked `<!-- SAMPLE COPY -->` and found by the pre-launch sweep, which now includes `SAMPLE COPY`. From a reference it takes only palette, structure and proportions, never name, logo, images or text, and the plan records how much of the style was really read. `AGENTS.md` sections 4, 5 and 8, `DOCUMENTATION.md` sections 6.1.1 and 7.4 and the README describe it.
- `legible help` is now a simple explanation of at most six lines (what it is, what you get, what it fits, how it works) followed by the command table and the state of the plan.
- Exact AI commands, always in English: `legible start`, `legible continue`, `legible help`, `legible flow off` and `legible flow on`, with a command table at the top of `AGENTS.md`, in the README and in `DOCUMENTATION.md` section 6.1.1. `run legible`, `ejecuta legible`, `start site` and similar phrases are no longer start commands: with no plan they get the short explanation of what `legible` is, which ends with the command list. With a plan, loose continue phrases in any language still work.
- Engine mode is now announced: the AI says `Engine mode on: <the change>` when it enters and ends its final message with `Engine mode off` and the record of the change. `DOCUMENTATION.md` section 5.0 gains a "control surface" table that lists every signal the AI reads (`FLOW_OFF.lock`, `SITE_PLAN.md`, `project_stage`, the user's message), who sets it, whether it persists and its precedence, and the routing diagram now starts with the lock and `legible help`.
- `FLOW_OFF.lock`: a maintainer's local switch created by `legible flow off` and deleted by `legible flow on`. While it exists the AI skips the interview, the plan and the explanations and treats the project as an ordinary repository, with no engine-mode confirmation; engine changes are recorded in the final message and here. It is listed in `.gitignore` and `tests/test_legible.py` fails if it exists, so it cannot ship in a zip unnoticed (the suite goes from 130 to 132 tests).
- AI workflow for building the base of a site. The AI first looks for `SITE_PLAN.md` in the zip. With a plan it continues it (on `continue` or any similar phrase in any language, or when nothing specific is asked); with no plan, `legible start` starts the work and the AI runs a twelve-question interview in three rounds (the site, the contact and offer, the design and gaps), proposes the pages, URLs and design direction for the user to confirm, and returns the zip with a short `SITE_PLAN.md` already inside; later sessions execute one phase each, update the plan and return the zip. Documented in `AGENTS.md`, `DOCUMENTATION.md` (sections 5.0, 5.4, 5.5, 6.1 and 6.2) and the README ("Build a site with an AI").
- `SITE_PLAN.md` format: briefing, URL map, at most ten phases sized for one free-plan session each (data; structure and URLs; brand tokens; component styles; layout and partials; brand assets; content in three phases; legal and close) with statuses (`pending`, `in_progress`, `done`, `blocked`), pending confirmations, engine notes, execution log, a **Later** list and a **Final state** section.
- Size limits so the plan stays a short base structure an AI can read in full each session: about 120 lines, at most two lines of detail per phase, a session budget of about three pages or three large files per phase, no per-page outlines or small-task checklists, Later items in one line, at most three log lines per session.
- `project_stage` in `src/data/site.json` (`template`, `in_progress`, `complete`): a coarse marker set by the AI when phase 1 starts and when the plan completes. The engine and the validator ignore it (the build, the strict validator and the 130 tests pass with it present), so no engine change is needed.
- Refinement mode: with `project_stage` `complete` and no `SITE_PLAN.md`, the AI does not run the flow (no interview, recovery, continuing or new plan); it works only on the part the user names. Starting over needs an explicit request and a confirmation.
- Recovery mode: when `project_stage` is `in_progress` (older zips without the field fall back to the sample values in `site.json`) but `SITE_PLAN.md` is missing, the AI audits the project, rebuilds a short plan from the evidence (phases `done` only when supported, nothing guessed) and asks the user to confirm it, instead of starting the interview from zero.
- Completion and maintenance: when the last phase is done the plan is marked `complete` and its **Final state** records the state of everything; attaching the zip later starts maintenance mode, which fixes or extends only the part the user names.
- With no plan, any request that is not a start command (and with a plan, any clear request other than continuing it) makes the AI first explain what `legible` is, what it fits, which checks it includes and how it is used; it warns about partial fits, things outside the base and engine changes, and waits for the user's decision (`AGENTS.md` section 1, `DOCUMENTATION.md` section 5.0).
- Built-in SEO checks are described as part of `legible` (`DOCUMENTATION.md` section 1.0, README "Validation"): generated metadata and JSON-LD, sitemap, `robots.txt`, `llms.txt`, strict validator and pre-launch sweep. The AI never asks the user whether to enable them.
- Verification rules for every phase except the last (`CHECK_STRICT=FALSE` only to review warnings from pending facts, never in the last phase) and for an AI that cannot run commands.
- `AGENTS.md` mode for one-session builds, and engine mode that also applies when a plan exists.
- Measurable plan checks: `wc -l SITE_PLAN.md` (120 lines or fewer) and a count of the phase rows (10 or fewer, 12 at most), run before delivering the plan and after every update; and `wc -c` on the files a phase will touch (about 50000 bytes at most) before it starts.
- A `Read:` line per phase, with a default table in `AGENTS.md` section 5, so a session reads only the sections and files it needs instead of the whole documentation.

### Changed

- Documentation only, no engine change. `AGENTS.md` section 5 ("Where the plan goes") and section 6 (Execution, step 5) now require the AI to verify the zip before returning it, by comparing `unzip -Z1` of the returned zip with the original's (minus the excluded folders) and reading the whole `diff`; a pilot once returned a zip without `tests/`, `src/static/` and the images after truncating the listing. `AGENTS.md` section 9 now says that the baseline (`unittest`, strict build and validator) applies to an adapted site too, since the suite passes there and skips only the `@ONLY_TEMPLATE` tests, and what to do when a test fails because of the site's own content: do not relax or skip it, record it and tell the user. `DOCUMENTATION.md` sections 5.0 and 7.3 point to both. Improvements 13 and 14 of the inventory.
- The plan's phases are resized for a session of a free-plan chat. The old single "design and brand" phase becomes four (brand tokens, component styles, layout and partials, brand assets) and "content" becomes three (home, services index and pricing; service pages; featured action, about and contact); legal pages and the close are one phase. The limit moves from five to ten phases (twelve with more than three service pages), detail per phase drops from four lines to two, and each phase has a session budget of about three pages or three large files. A phase the site does not need (for example the brand tokens when the base look is kept) stays in the plan as `done` with "not needed". The AI never fabricates `og-image.png`, `apple-touch-icon.png` or `favicon.ico`: the sample files stay and are listed as pending until the user supplies the real ones.
- `AGENTS.md` is easier to follow as a prompt, with no change of rules: an "At a glance" summary at the top; section 1 is a single decision table (plan, `project_stage`, request, mode, first words) and section 3 only lists the modes; the longest paragraphs are split into short bullets; and the end of section 8 says what to do when a case is not covered (stop, name the gap, ask one question).
- One source of truth for the AI method: `AGENTS.md` holds the procedures, numbers, limits and commands, and `DOCUMENTATION.md` section 5.0 keeps the reasoning and the reference tables and points to `AGENTS.md` instead of repeating them (the phase catalogue, the plan size limits, the steps of each mode and the verification rules were written in both). New ground rule 7 in `DOCUMENTATION.md` section 0.1 says so, and `AGENTS.md` says that it wins if the two differ.
- `src/data/site.json` now carries `"project_stage": "template"`, as the documentation already stated; the engine and the validator ignore it.
- `DOCUMENTATION.md` section 2.2: alignment of the `SITE_PLAN.md` line.
- "Integrated tools" is now "interactive features" in `AGENTS.md`, the README and `DOCUMENTATION.md`: it means calculators, booking, forms with a backend and maps, which are outside the base. It was previously read as if `legible` lacked tools.
- `AGENTS.md` is rewritten: the default job is building a site by changing only `src/`; the engine, the tests and the architecture are not to be improved on the AI's own initiative, and deployment is outside the process. An engine change is a minimal exception that must be recorded in the plan.
- `AGENTS.md` rule 5 points to `DOCUMENTATION.md` section 7.4 explicitly, so it is not confused with the engine exception in `AGENTS.md` section 7.
- `DOCUMENTATION.md` section 6.1 (one-session prompt) is now 6.3 and is optional; the briefing template is an optional shortcut for the interview.
- The slot markers (categories, cities, offers) are computed in one place, `sample_slots()` in `legible/build.py`, with the sample values in the constants `SAMPLE_CATEGORIES`, `SAMPLE_CITIES`, `SAMPLE_OFFERS` and `SAMPLE_FREE_OFFER`, instead of about thirty near-identical lines in `build()`. The output of the template is identical byte for byte, minified and unminified.
- `src/data/entity.json` now lists the six sample `knowsAbout` entries as plain text (`Service 1`…`Service 6`) instead of the markers `{{service_category_1}}`…`{{service_category_6}}`. The template used to rely on the engine's hidden sample values; now the sample data lives in `src/data/`, where the pre-launch sweep finds it, and the engine's fallback only fires when data is really missing. The published output does not change.

### Fixed

- `llms.txt` now resolves `{{markers}}` also in the blocks the engine generates (`render_llms()` takes an optional `replacements`), so a locale override such as `llms_guides_description` can name the business. Before, a marker in those blocks stopped the build as unresolved. Builds that worked before are unchanged.
- The link text of the guide and article cards (`card_read_guide`, `card_read_article`) is HTML-escaped: it lands in an `aria-label`, where a `"` in a locale override would have broken the attribute. The default texts have no special characters, so the output is unchanged.
- Contact data in `entity.json` (`email`, `contactPoint.telephone`, `address`) is now truly optional: a missing key, or an explicit `null` (not only an unresolved `{{placeholder}}`), falls back cleanly to `src/data/site.json` instead of crashing the build with an unreadable `TypeError` or `AttributeError`. New `_get()` helper walks nested entity fields without raising, and `_unwrap_placeholder()` now treats `None` the same as an unresolved marker. `dist/` of the sample site is unchanged; 7 new regression tests (`TestOptionalContactData`, 132 → 139).
- Sample values for offers, cities and service categories no longer reach published pages silently. When `entity.json` gives no value for a numbered marker (`{{service_N_name}}`, `{{service_N_price}}`, `{{service_N_price_number}}`, `{{city_N}}`, `{{service_category_N}}`, and the name of the free offer), the build still substitutes a sample value (`Service 2`, `$149`, `City 4`…) but now warns for every slot whose sample value ends up in the published text, naming the markers, why the slot is empty (`hasOfferCatalog has 1 offer`) and the files that use them. A sample value that no page, text or schema node uses stays silent. The new `build.py --strict` turns these warnings into errors, and `build.sh` passes it when `CHECK_STRICT=TRUE` (the default), so a strict build fails exactly like the validator's warnings do and `CHECK_STRICT=FALSE` still lets a phase in progress build. Found as a new finding of the pilot review: before this, a site with one offer and one city published `Service 2`, `$149`, `$49/mo`, `City 2` and `City 4`, and neither the build nor the validator said anything. 13 new regression tests (`TestSampleFallbacks`, 139 → 152).
- An offer in `hasOfferCatalog` with no `price` no longer publishes the word `None`: it counts as an empty slot (sample value plus warning). `knowsAbout`, `areaServed` and `hasOfferCatalog` set to `null`, or an offer that is not an object, no longer raise a `TypeError`; a `knowsAbout` that is not a list stops the build with a message that names the field.
- The closing strip of the `/guides/` and `/blog/` indexes no longer assumes a WhatsApp number or an email. Its contact line is built from the channels the site really has: with no telephone it shows only the email (new locale key `lead_strip_contact_email_only`), with no email only WhatsApp (`lead_strip_contact_whatsapp_only`), and with neither it shows no line and keeps the button. Before this, a site with no telephone published `<a href="">WhatsApp</a>` in both indexes and the validator failed, and one with no email published `mailto:`. New optional `generated_content.lead_strip.contact_html` in `site.json` replaces the whole line (HTML, `{{markers}}` allowed, an empty string removes it). `_lead_strip_html()` takes `has_email` and `has_whatsapp` (both default to `True`), `render_guides_index()` and `render_blog_index()` take an optional `lead_strip`, and `en.json`/`es.json` gain the two keys. With both channels the output is identical byte for byte, with guides and blog present, minified and unminified. 9 new regression tests (`TestLeadStripContact`, 152 → 161).
- The test suite no longer depends on the template's sample pages or data. `tests/test_legible.py` used to fix `services/<first service>/` at import time (`_SERVICES[0]` raised `IndexError` in any project without a `services/` folder, so the suite did not even load) and 31 lines in all named a sample page (`services/`, `pricing/`, `about/`, `privacy-policy/`…) or sample data (the city, the region, `hello@example.com`). Now the tests ask for "a page that exists": new helpers `page_routes()`, `pick_page()` (by predicate, with the home page as last resort), `related_page()`, `write_stub_page()` and `built_page()`, and `use_marker_in_a_page()` in `TempProject`; the city, region, email and domain are read from `SITE` (`src/data/site.json`). Guide and blog test pieces link to any existing page (`RELATED_PAGE`, home if there is no other). `test_sample_service_has_updated` becomes `test_every_sample_page_has_updated` (`@ONLY_TEMPLATE`). Checked on the template and on three adapted copies (pages renamed; pages renamed with another domain, city and email; no `services/`, `pricing/` or `featured-action/`): the suite passes in all of them, skipping only the `@ONLY_TEMPLATE` tests. `legible/` and `src/` are untouched, so `dist/` of the template is identical byte for byte. 9 new regression tests (`TestPageLookup`, `TestSuiteIsIndependentOfTheSamplePages`, 178 → 187): the helpers; a static guard that fails if a test names a sample page or sample data (a line may opt out with `# template-only`); and a probe that renames every sample page, changes the domain, city and email and runs the page-editing test classes there. `DOCUMENTATION.md` section 7.3 describes the rule.

## [1.0.0] - 2026-10-25

First release.

### Added

- `{{target_audience}}` is now a derived marker and is escaped for HTML and JSON-LD like the others; a zone name such as `Rock & Roll <City>` no longer breaks the footer.
- A text in `texts.json` can reference another text in any order (up to 5 passes); circular references still fail with a marker that has no value.
- A clear error when an `areaServed` entry is not an object, and an error message for unresolved derived markers that points to `entity.json` or `site.json`.
- The sitemap `lastmod` and the `updated` front matter can no longer disagree silently: when both exist they must match or the build fails. The sample service page now has `updated`.
- The validator's internal link keys now always use `/` (`as_posix()`), so on Windows pages should no longer be reported as orphans and anchors to other pages should be checked. Not yet run on Windows.
- The `legible/dev.py` file watcher now ignores files that disappear while it is scanning `src/`, instead of letting the watcher thread die silently.
- The pre-launch sweep (README and `DOCUMENTATION.md` section 7.4) is now the same single-quoted command in both places, so the price patterns match; it also flags sample hours, deadlines, currency and country.
- The sample bundle price is now lower than the two services it combines.
- The unresolved-marker error says "first found on page …" (the marker may appear on several pages), and the redundant `target_audience` parameter of `compose_page` was removed.
- An empty `SITE_URL` falls back to `site_url` in `src/data/site.json`, and `build.sh` warns (without failing) when the output still uses the sample domain `YOUR-DOMAIN.com`.
- Static-site generator (`legible/build.py`) written with the Python standard library only, with no client-side JavaScript and no third-party requests. Requires Python 3.8 or newer.
- Business facts kept in three data files (`src/data/site.json`, `entity.json`, `texts.json`) and propagated through `{{markers}}`; an unresolved marker stops the build and names the marker and the page.
- Generated output: HTML pages, one CSS file (optionally minified), a Schema.org JSON-LD `@graph` per page, `sitemap.xml`, `robots.txt` and `llms.txt`.
- Optional guides and blog collections with generated indexes and configurable folder paths (`collection_paths`).
- Strict validator (`legible/check_site.py`) for the compiled site: metadata, headings, links and assets, placeholders, JSON-LD references, sitemap and `robots.txt`. In strict mode warnings also fail the build.
- `legible/build.sh`, which builds and then validates, driven by `SITE_URL`, `CSS_MINIFY` and `CHECK_STRICT`.
- Local development server (`legible/dev.py`) that rebuilds when `src/` changes, and `legible/run_all.py`, which runs tests, build with validation and the server in order.
- English and Spanish engine-generated strings (`legible/locales/en.json` and `es.json`); other languages need a locale file and a row in the `LANGUAGES` table of `build.py`.
- Sample site of 11 pages (including the 404 page) with neutral, fictional content, to be replaced before publishing.
- Regression suite of 130 `unittest` tests.
- Documentation: `README.md`, `DOCUMENTATION.md` (reference, marker catalogue, validator rules and the guide and briefing template for AI-generated sites) and `AGENTS.md` (entry point for AI agents).

## How to add an entry

1. Write changes under `[Unreleased]` as you make them, grouped under `### Added`, `### Changed`, `### Fixed` or `### Removed`. Omit empty groups.
2. When you release, rename `[Unreleased]` to `[X.Y.Z] - YYYY-MM-DD`, then add a new empty `## [Unreleased]` above it.
3. Use the version rules from Semantic Versioning: **MAJOR** for a breaking change (prefix its entry with `**Breaking:**`), **MINOR** for compatible new functionality, **PATCH** for fixes that do not change behaviour.
4. Use the same number in the Git tag (`vX.Y.Z`) and the release branch (`release/X.Y.Z`).
