## Overview

`legible` turns the files in `src/` into a static website for one main entity: a business, a project or a person. It generates page metadata, Schema.org JSON-LD, a sitemap, `robots.txt` and `llms.txt`, then validates the compiled output against a built-in checklist.

The aim is predictable, inspectable output — not guaranteed rankings, indexing, rich results, traffic or AI citations. The included site is generic sample content; replace it with your real facts before publishing (see [Before launch](#before-launch)).

The technical reference — architecture, data model, marker catalogue, validator rules — lives in [`DOCUMENTATION.md`](DOCUMENTATION.md). The procedure an AI assistant follows to adapt the base is [`AGENTS.md`](AGENTS.md).

## Requirements

- Python 3.10 or newer. No third-party packages for building, validating or testing.
- No client-side JavaScript and no external resources: one stylesheet, system fonts.
- `bash` is only needed for the `legible/build.sh` convenience wrapper; `python3 legible/build.py --all` works on its own everywhere Python runs.

## Quick start

Run these from the project root:

```bash
python3 -B -m unittest discover tests   # regression suite
python3 legible/build.py --all          # build, validate (strict) and print what is left to publish
python3 legible/dev.py                  # local server at http://localhost:3001/, rebuilds on change
```

Open `http://localhost:3001/` while the server runs (not with `file://`: internal links are absolute paths). Stop it with `Ctrl+C`.

Set `site_url` in `src/data/site.json` to the real HTTPS origin before deploying; `SITE_URL` overrides it (for CI and previews).

## Build a site with an AI

The zip is a generic base. Attach it to an AI assistant and give one command, always in English whatever language you speak:

| Command | What happens |
|---|---|
| `legible start` | No data: a short interview (two rounds, at most eight questions), then the site is built in the same session |
| `legible start name: …; activity: …` (or a URL, or attached images) | Quick start: no interview, built from what you gave |
| `legible continue` | Keeps working on a site already adapted |
| `legible help` | Explains `legible` and this command list |

The assistant follows [`AGENTS.md`](AGENTS.md): it edits `site.json`, `entity.json`, the pages, the menu and the design tokens, never invents a fact (a phone, an address, a price, a legal detail) it was not given, and marks any short placeholder copy it writes with `<!-- SAMPLE COPY -->`. It does not touch `legible/` or `tests/`, and it does not handle deployment. A request to change the engine itself only proceeds as an explicit, confirmed **engine mode**, recorded in `CHANGELOG.md`.

## Configure a site

- `src/data/site.json` — the single source of facts and settings: identity, contact, place, legal data, menus (`nav`, `legal_nav`), interface wording (`ui`).
- `src/data/entity.json` — the Schema.org node of the main entity and the `WebSite` node, in JSON-LD.
- `src/pages/` — one folder per page (`index.html` inside); copy `src/pages/example/` for a new one.
- `src/css/site.css` — one stylesheet; every colour is a token in `:root`.

Write `{{key}}` in a page, a partial or a static text file to use a value from `site.json`, or one of the markers the build derives (page URL, date, generated menus…). The build fails on an unresolved or unknown marker, with a message that names it. The full data model is in [`DOCUMENTATION.md`](DOCUMENTATION.md).

## Before launch

```bash
python3 legible/check_site.py --prelaunch
```

Lists every sample value still left (an example domain or contact detail, a page carrying `<!-- SAMPLE COPY -->`) and exits non-zero while anything is pending. Empty output means it is ready to publish.

## Language support

Set `"language": "en"` or `"language": "es"` in `site.json`: the interface wording generated by the engine (menus' fixed labels, skip link, WhatsApp button…) switches language. It does not translate your own page content, which you write and update yourself. See [`DOCUMENTATION.md`](DOCUMENTATION.md) to add another language.

## Validation

`legible/check_site.py` checks the compiled output: metadata, headings, images, links, JSON-LD, sitemap and `robots.txt`. Strict mode (the default under `--all`) makes warnings fail the build too. The full rule table is in [`DOCUMENTATION.md`](DOCUMENTATION.md).

## Deployment

Publish `dist/` to any static host (Cloudflare Pages, GitHub Pages, Netlify, Render, S3, Nginx):

```text
Build command:      python3 legible/build.py --all
Publish directory:  dist
Environment:        SITE_URL=https://your-domain.com
```

A failed validation exits non-zero, so a host that checks the exit code will not publish a broken build. Details and alternatives (unminified output, non-fatal warnings) are in [`DOCUMENTATION.md`](DOCUMENTATION.md).

## Scope and limitations

- A focused generator for small sites with one main entity, not a CMS or a general publishing framework.
- The built-in checks confirm structure and honesty of output, not search rankings, indexing or AI citations.
- The legal pages are templates, not legal advice: review them before publishing.
- Interactive features (a booking engine, a cart, a form with a backend, a map) need JavaScript or a backend and are outside the base.

## Contributing

`legible/` and `tests/` are deliberately fixed (see `AGENTS.md`); a change there needs an explicit, named reason and keeps the suite and the strict validator green. Run the quick-start checks above before submitting, and record any engine change in `CHANGELOG.md`.
